# 踩过的坑

原型阶段和 v1.0 重构时实测遇到的，改相关代码前先看一眼。

## 布局

- **`tiling()` 和选图必须是纯函数**。只用 block 坐标、块序号、种子做哈希，不读全局状态、不用 `Math.random`。
  一旦带了随机，拖走再拖回来图就变了。`test/layout.test.mjs` 有专门的用例。
- 原型的选图对每块独立哈希，一个 4×4 block 里偶尔会出现同一张图两次。v1.0 改成 block 起点哈希 + 与图片数互质的步长，
  图片 ≥ 16 张时同一 block 内不重复。

## 交互

- **`setPointerCapture` 会改 click 的 target**：捕获后 click 派到 stage 上，`e.target.closest('.tile')` 拿不到块。
  点图要在 pointerup 里判「移动 < 8px」，再用 `document.elementFromPoint` 找块。
- **pointerup 打开大图后，同一次点击产生的 click 会立刻把它关掉**：打开后 400ms 内不响应关闭。
- **`[hidden]` 会被 `display:flex` 覆盖**：面板写了 `display:flex` 后 `hidden` 失效，页面一打开就是一层遮罩。
  必须有 `[hidden]{display:none!important}`。
- 惯性按最后约 90ms 的采样算速度，按时间（ms）而不是帧积分，120Hz 屏和 60Hz 屏滑得一样远。

## 后端

- **`http.server` 按 latin-1 解请求行**：没编码的中文 `?path=图片` 会变成乱码 → 403。
  前端一律 `encodeURIComponent`；v1.0 服务端也会尝试把 latin-1 还原回 UTF-8。
  注意 Windows 的 Git Bash 里 `curl -G --data-urlencode '中文'` 编码出来的不是 UTF-8，测接口时直接写 `%E5%9B%BE...`。
- **`/api/images` 是全量递归扫描**：1.2 万张约 1–5 秒（取决于磁盘缓存冷热）。前端只在切文件夹时请求，
  服务端过期后先返回旧清单、后台重扫，不会让请求卡在扫描上。
- **缩略图冷启动是 CPU 密集的**：4K PNG 约 0.3 秒一张。同屏几十张第一次打开会有几秒空窗，
  靠预生成解决；v1.0 的加载队列保证离视口中心近的先出来。
- ES Module 要求 JS 的 `Content-Type` 是 JavaScript MIME，`application/octet-stream` 会直接加载失败。

## 验证

- `chrome --screenshot` 不等图片加载，截出来是黑的。要走 CDP 等图片 onload（`test/e2e.mjs`）。
- 在 NAS 的应用容器里起 chromium 会 core dump，要在独立容器里跑。
